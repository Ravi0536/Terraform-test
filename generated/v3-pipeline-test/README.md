# v3 pipeline test root

Target for end-to-end runs of the IaC Operations v3 pipeline. Codified
resources arrive here as a pull request against `tos-v3-pipeline-test`, so
`main` never sees an experimental run.

Layout matches `generated/tos-demo` and `generated/cloudtrail-adoption`
deliberately: a provider pin and nothing else, so anything else in a diff was
generated by TOS.

## Management root settings

| Setting | Value |
|---|---|
| Repository | `Ravi0536/terraform-test` |
| Base branch | `tos-v3-pipeline-test` |
| Root path | `generated/v3-pipeline-test` |
| Tool family | `terraform` |
| Adapter type | `s3_backend` |

## Two settings that decide whether a run finishes

**`root_path` and the delivery `path_prefix` must be the identical string.**
Compared for exact equality, not prefix-match. A mismatch fails with
`deployment operation does not have one exact root route`, and the generation
cannot be re-delivered because its branch name derives from the generation id.

**A management root must be bound at codify time.** Without one there is no
route, so no pipeline plan is pinned and the operation renders the v2 rail
with no plan note.

## Checks

`.github/workflows/phase15-terraform.yml` lists this branch in its
`pull_request.branches`. That entry is required: GitHub reads the check set
from the BASE branch's workflow, so without it a PR targeting this branch
reports no checks at all and the pipeline waits at Run checks forever.

The job runs `terraform fmt -check -recursive`, `init -backend=false` and
`validate` across `generated/`, so a malformed delivery fails the gate rather
than reaching approval.

## Confirming a v3 run

The generator logs exactly one line per codification:

```
worker: pinned pipeline plan for operation op_... (root iar_...)
```

`GET /v3/iac/operations/{id}/plan` then answers 200 with that plan, and the
console shows stack chips plus a plan note under the rail. The three
non-success outcomes each name their own cause: no management root, store
cannot pin, or the underlying error.
